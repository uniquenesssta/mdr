# R11-09 — Replay/Recovery (Transaction Application, Tail Truncation, Prefix Validation, Safe Snapshot Rebuild)

- 基线与前置：本 Atomic 建立在本地 R11-08 Journal Entry/Append 改动之上（R11-04 至 R11-09 均在本地推送/未推送状态见下）。**用户已明确指示本轮不再等待真实 CI**：R11-04 至 R11-08 已推送（PR #17），但触发的 12 个 workflow 里失败的三个一次性门禁（R10-11/R10-12/R11-03）和全部 Stage 0-7 阶段级门禁均确认是推送前就已存在、与 Stage 11 无关的历史遗留问题；`.github/workflows/` 目前完全没有覆盖 R11-04 到 R11-08（现含 09）的专属门禁文件。按用户指示，本 Atomic 不再以真实 CI 结果作为开始条件，仅依赖本地验证结果推进。
- 任务书依据：执行 Stage 11 Atomic 11.9 Replay/Recovery。目标是把事务应用、日志截断尾部处理、版本链前缀校验、安全快照重建从 `document_store.rs` 提取到独立文件；必须产出 recovered/message 逐字一致。
- Replay 边界：新增 `src-tauri/src/document_store/journal/replay.rs`，拥有两个函数：
  - `apply_transactions(&mut String, &[DocumentTransaction]) -> Result<(), String>`——原样迁移自 `document_store.rs` 顶层同名函数，逐条事务按 `from` 降序应用、调用 `validation::transaction_byte_range` 计算字节范围。此函数同时被 `save_document_inner`（保存时对新事务的即时应用）与 replay 循环（重放历史日志）共用，任务书 11.9 明确将“事务应用”列为本 Atomic 内容，故随复原逻辑一并迁移，而非留在 store 编排层。
  - `replay_journal(&mut StoredDocument, &[u8], notes: Vec<String>) -> JournalReplay`——原样迁移自 `load_document_from_disk` 内的逐行解析循环（找行尾、跳过空白行、UTF-8 解析失败/JSON 解析失败/版本链断裂三类提前终止、`next_version <= document.version` 的陈旧条目跳过、事务应用失败提前终止），返回 `{ notes, stale_entries, valid_journal }`；`document.journal_bytes` 的赋值保留在循环结束处，与原实现同一位置。
  - **关键行为保留点**：`notes` 参数接收调用方已经从快照加载阶段收集到的提示（例如某一槽校验失败），replay 过程中的新提示追加在其后而非另起一个列表——这精确对应原实现里 `recovery_notes` 是同一个 `Vec` 从快照阶段贯穿到日志阶段的行为：若某槽损坏但日志本身重放干净，原实现仍会因为 `recovery_notes` 非空而进入"已恢复"分支并写出新快照。若不做这层参数传递，直接让 replay 只看自己的空提示列表，会静默丢失这一恢复路径，是本次迁移中最容易引入的行为回归，已用新增测试 `replay_journal_carries_forward_notes_seeded_from_snapshot_loading` 专门覆盖。
- Recovery 边界：新增 `src-tauri/src/document_store/journal/recovery.rs`，拥有两个函数：
  - `recover_from_snapshot_notes(root, &mut StoredDocument, &[String]) -> Result<(), String>`——无日志文件时的分支：提示非空则置 `recovered = true`、组装“检测到存储异常，已从可用快照恢复到版本 {}：{}”文案（逐字保留）、调用 `write_snapshot`。
  - `recover_from_journal_replay(root, &mut StoredDocument, original_bytes: &[u8], JournalReplay) -> Result<(), String>`——有日志文件时的分支：`replay.notes` 非空则置 `recovered = true`、组装“检测到存储异常，已恢复到版本 {}：{}”文案（逐字保留，含原有中文行内注释“将已经验证的连续增量折叠为新快照…”一并迁移）、调用 `write_snapshot` 并清零 `journal_entries`/`journal_bytes`；否则若 `stale_entries` 或 `valid_journal != original_bytes`（即发生了陈旧条目剔除或尾部截断），把 `valid_journal` 原子写回日志文件——对应任务书“截断尾部”的落盘动作。
- 编排保持：`document_store.rs` 的 `load_document_from_disk` 收窄为：加载快照 → 无快照且有提示则报错、无快照无提示返回 `None` → 有日志文件则 `replay_journal` + `recover_from_journal_replay`，否则 `recover_from_snapshot_notes`。不决定何时触发保存后的快照阈值判定（`SNAPSHOT_ENTRY_LIMIT`/`SNAPSHOT_BYTE_LIMIT`/`force_snapshot`，仍在 `save_document_inner` 里）。`save_document_inner` 对 `apply_transactions` 的调用点签名不变，只是来源改为 `journal::apply_transactions`。
- 导入清理：`document_store.rs` 顶层不再需要 `transaction_byte_range`（随 `apply_transactions` 一并迁移）与 `write_atomic`（随日志截断写回一并迁移到 `recovery.rs`），已从 `use validation::{...}`/`use repository::{...}` 中移除；`pub(crate) use types::{...}` 里的 `DocumentTransaction` 在本次改动前是靠 `apply_transactions` 函数签名里的裸名引用“顺带”消除 unused-import 告警，迁移后该裸名引用消失，`cargo check` 复验确认其在 crate 内已无其他消费者（`grep -rn` 确认零外部引用），故一并从该 re-export 列表移除；测试模块改为直接 `use super::types::{DocumentTransaction, TextChange};`。`use journal::{...}` 列表内部顺序按 rustfmt 要求排列（`append_journal` 先于 `apply_transactions`）。
- 测试迁移：`document_store.rs` 原有的 `applies_utf16_changes_for_chinese_and_emoji` 单元测试随 `apply_transactions` 一并迁移到 `journal/replay.rs`，未在原位置保留重复断言。
- 兼容夹具：`document_store_compatibility.rs` 无需改动——冻结 token（`0xcbf29ce484222325`、`0x100000001b3`、`encode_utf16`、`snapshot-{slot}.md` 等）均已在 `document_store.rs`/`types.rs`/`validation.rs`/`snapshot/integrity.rs` 的既有扫描范围内，本次迁移未触及任何新增冻结 token 所在文件。
- 新契约测试：`journal/replay.rs` 自带 6 项单元测试——沿用的 `applies_utf16_changes_for_chinese_and_emoji`，加上连续版本链正确应用并零提示、陈旧条目被跳过、版本链断裂在首个坏条目处停止并记录提示、尾部截断记录停止并记录提示、以及关键的“种子提示随重放结果一并携带”回归测试。`journal/recovery.rs` 自带 5 项单元测试——快照提示为空时不动作、快照提示非空时置位并重建快照、日志重放无提示时不动作、日志重放陈旧无提示时原子写回截断后的日志、日志重放有提示时置位重建快照并清零日志计数器。`document_store.rs` 原有的 `repairs_truncated_journal_after_last_valid_transaction`（模拟半条记录截断恢复）与 `falls_back_to_other_snapshot_slot_when_latest_is_corrupt`（模拟槽损坏回退）两个端到端集成测试保持不动、继续通过，作为 replay/recovery 迁移后完整链路的验证，且后者恰好覆盖了本次特别关注的“快照提示携带进日志分支”路径的姊妹场景（快照损坏但走的是 `recover_from_snapshot_notes` 分支，因为该用例本身没有日志文件）。
