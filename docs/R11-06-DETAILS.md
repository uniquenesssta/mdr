# R11-06 — Metadata/Integrity (Hash, Byte Count, Meta Parse/Validate)

- 基线与前置：本 Atomic 建立在本地 R11-05 Snapshot Slots 改动之上（R11-03/04/05/06 均尚未提交/推送）。**本地尚未推送到远程，均未经过真实 GitHub Actions CI 验证**；真实 CI 全部通过前不得视为已收口，不进入 R11-07。
- 任务书依据：执行 Stage 11 Atomic 11.6 Metadata/Integrity。目标是把 FNV-1a64 哈希算法、内容字节数/哈希一致性校验、以及快照元数据（`SnapshotMeta`）的构建与解析从 `document_store.rs` 提取到独立模块；必须产出 fnv1a 结果一致。
- Metadata/Integrity 边界：新增 `src-tauri/src/document_store/snapshot/integrity.rs`，拥有 `fnv1a64`（哈希算法本体）与 `content_integrity_valid`（给定内容、期望字节数、期望哈希，返回两者是否同时匹配）。新增 `src-tauri/src/document_store/snapshot/metadata.rs`，拥有 `build_snapshot_meta`（由 version/title/updated_at/content 构建 `SnapshotMeta`，字节数与哈希内部经 `integrity` 计算）与 `parse_snapshot_meta`（反序列化字节为 `SnapshotMeta`，失败返回 `None`）。
- 类型可见性调整：`SnapshotMeta`（`types.rs`）及其字段的可见性从 `pub(super)`（仅 `document_store` 可见）放宽为 `pub(in crate::document_store)`（`document_store` 及其全部子模块可见），并新增 `SnapshotMeta::new(...)` 构造函数（同样 `pub(in crate::document_store)`），使两层深的 `snapshot::metadata` 能够命名该类型并通过唯一构造入口创建它；字段本身未从 `types.rs` 之外获得直接读取权限之外的东西——`document_store.rs` 读取字段的方式未变（仍是 `meta.field`，`pub(in crate::document_store)` 覆盖了原 `pub(super)` 的全部既有读者）。这是跨越一层子模块边界访问私有 DTO 类型的必要放宽，不是无关的可见性扩大。
- 不迁移范围：快照写入的 fsync/rename 顺序与两槽加载编排（`write_snapshot`/`load_document_from_disk` 主体、快照槽存在性探测、恢复标记与日志重放）均原地不动，划给 11.7 Writer/Loader 与 11.9 Replay/Recovery，本次未提前跨 Atomic 抽取。`fnv1a64` 虽然物理落在 `snapshot/integrity.rs`（按任务书目标目录树），但也继续被 `document_store.rs` 中与快照无关的 `heading_id`（标题锚点 ID 生成，属于后续 11.10 Index Builder 的职责）调用——这是共享同一个无状态哈希原语，不构成职责越界。
- 编排保持：`document_store.rs` 的 `read_snapshot` 改为调用 `parse_snapshot_meta` 解析 meta 字节、`content_integrity_valid` 校验内容；`write_snapshot` 改为调用 `build_snapshot_meta` 构建元数据。调用顺序、Mutex 作用域、错误传播语义、`None`/恢复分支行为均未改变。
- 兼容夹具：`document_store_compatibility.rs` 新增 `SOURCE_DOCUMENT_STORE_SNAPSHOT_INTEGRITY`（`include_str!` 引入 `snapshot/integrity.rs`）并纳入 `current_source_contains` 的扫描范围——冻结 token `0xcbf29ce484222325`、`0x100000001b3`（FNV-1a64 的 offset basis 与 prime 常量）随 `fnv1a64` 函数体一起迁移，若不扩展扫描范围会导致 `manifest_pins_the_exact_pre_rewrite_source_and_format_vocabulary` 误报"token 丢失"。这与 R11-03 把扫描范围扩展到 `validation.rs`/`paths.rs` 是同一处理方式：不改变 fixture 内容或兼容算法本身，只让扫描跟随代码搬迁。
- 新契约测试：`snapshot/integrity.rs` 自带 2 项单元测试——`fnv1a64` 对已知参考摘要（空输入、`"a"`）的精确匹配，`content_integrity_valid` 要求字节数与哈希同时匹配（任一不符即判定无效）。`snapshot/metadata.rs` 自带 3 项单元测试——`build_snapshot_meta` 正确计算字节数与哈希、`parse_snapshot_meta` 序列化后往返一致、`parse_snapshot_meta` 对非法 JSON 返回 `None`。
- 受保护范围：未修改 `src-tauri/src/main.rs`、`Cargo.toml`、`Cargo.lock`、`document_store/validation.rs`、`document_store/paths.rs`、`document_store/repository.rs`、`document_store/snapshot/slots.rs`、任何生产依赖、Tauri command 名称、DTO JSON 形状（`SnapshotMeta` 序列化输出未变，仅 Rust 内部可见性变化）、磁盘布局、UTF-16/恢复语义。`types.rs` 的改动仅为可见性放宽与新增构造函数，字段名/类型/serde 标注/JSON 契约完全不变（`persistence_json_snapshots_remain_exact` 测试原样通过）。无新增生产依赖。
- 验证：本地执行（Rust 工具链 `rustup override set 1.88.0` 锁定，与 CI 一致）：`cargo test` 39 单元 + 5 兼容 = 44/44 通过（较 R11-05 的 39/39 净增 5：integrity 2 + metadata 3）；`cargo clippy --all-targets -- --deny warnings` 通过；`cargo check` 通过；`rustfmt --check` 对新文件 `snapshot/integrity.rs`、`snapshot/metadata.rs` 及改动过的 `snapshot/mod.rs`、`types.rs`、`tests/document_store_compatibility.rs` 执行并通过（`document_store.rs` 保留其非完全 rustfmt-canonical 的既有格式，未做无关全文件格式化）；`npm test` 344/344 通过；`npm run verify:architecture` 通过；`npm run build` 通过。未运行 `npm run test:browser:contract`、`npm run test:browser`、Tauri release build——本 Atomic 只改变 Rust 内部模块边界与一个 DTO 类型的可见性，未改变任何 Tauri command 签名、JSON 契约或前端调用路径。
